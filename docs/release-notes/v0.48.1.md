# v0.48.1

**Release Date:** 2026-02-10
**Breaking Changes:** No

## Summary

Bug fixes for init-only indexer overrides and three attribute propagation gaps discovered during Rocks integration testing.

## What's Fixed

### Init-Only Indexer Overrides on Classes (Bug #35)

When stubbing a class (abstract or virtual) that has an indexer with an `init` accessor, the generated Impl class override used `set` instead of `init`, producing CS8853: "must match by init-only of overridden member". This prevented `[KnockOff<T>]` and `[KnockOffBase<T>]` from being used on any class with init-only indexers.

```csharp
// This abstract class could not be stubbed before this fix:
public abstract class InitIndexerBase
{
    public abstract int this[string key] { get; init; }
}

// Both patterns now work:
[KnockOff<InitIndexerBase>]          // Pattern 6: Inline Class
public partial class MyTests { }

[KnockOffBase<InitIndexerBase>]      // Pattern 3: Standalone Class
public partial class MyStub { }
```

**Root cause:** `InlineClassImplIndexerModel` lacked an `IsInitOnly` field, so `ClassRenderer` and `StandaloneClassRenderer` always emitted `set` for indexer overrides. Properties already handled this correctly.

**Affected patterns:** 3 (Standalone Class), 4 (Generic Standalone Class), 6 (Inline Class), 9 (Open Generic Class). Interface patterns (1, 2, 5, 7, 8) were not affected.

**Files changed:**
- `Model/Inline/InlineClassStubModel.cs` — Added `IsInitOnly` to `InlineClassImplIndexerModel`
- `Builder/ClassModelBuilder.cs` — Pass `IsInitOnly` from symbol
- `Builder/StandaloneClassModelBuilder.cs` — Pass `IsInitOnly` from symbol
- `Renderer/ClassRenderer.cs` — Conditional `init`/`set` keyword
- `Renderer/StandaloneClassRenderer.cs` — Conditional `init`/`set` keyword

### `[AllowNull]` Not Preserved on Class Property/Indexer Setters (Gap #18)

When a class had a property or indexer with `[AllowNull]`, the generated override didn't suppress CS8765 ("Nullability of type of parameter doesn't match overridden member"). For interface stubs, the attribute was only checked on setter parameters, missing cases where `[AllowNull]` is applied at the property level.

**Root cause:** Interface pipeline only checked `setterParam.GetAttributes()`, missing property-level `[AllowNull]`. Class pipeline had no `SetterHasAllowNull` detection at all for properties or indexers.

**Affected patterns:** All — interface (1, 2, 5, 7, 8) for property-level attribute; class (3, 4, 6, 9) for full pipeline.

### `[DoesNotReturn]` Not Propagated to Method Overrides (Gap #19)

When a class had a method marked `[DoesNotReturn]`, the generated override didn't carry the attribute, producing CS8770 ("Method lacks [DoesNotReturn] annotation to match implemented or overridden member").

**Root cause:** `DoesNotReturn` was completely absent from the class stub pipeline — not detected in models, not passed through builders, and not emitted in renderers.

**Affected patterns:** 3 (Standalone Class), 4 (Generic Standalone Class), 6 (Inline Class), 9 (Open Generic Class).

### `[SetsRequiredMembers]` Not Copied to Generated Constructors (Gap #11)

When stubbing a class with `required` members and a constructor marked `[SetsRequiredMembers]`, the generated constructor lacked the attribute, producing CS9039. The generator also only collected required properties from virtual/abstract members, missing non-virtual required properties and required fields from the class hierarchy.

**Root cause:** Constructor attribute detection only checked virtual members. Required member collection didn't walk the base type hierarchy or check `IFieldSymbol`.

**Affected patterns:** 3 (Standalone Class), 4 (Generic Standalone Class), 6 (Inline Class), 9 (Open Generic Class).
