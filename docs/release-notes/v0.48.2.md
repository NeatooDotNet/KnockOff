# v0.48.2

**Release Date:** 2026-02-13
**Breaking Changes:** No

## Summary

Bug fix for CS0453 compilation error in class stubs, and new Default Interface Method (DIM) support for interface stubs.

## What's New

### Default Interface Method (DIM) Support

Interface stubs now execute Default Interface Methods when interceptors are unconfigured, matching the `base.Method()` fallback behavior of class stubs.

Previously, KnockOff generated explicit implementations for all interface members — including those with default implementations — routing everything through interceptors. Unconfigured DIM members returned `default(T)` instead of executing the default implementation.

**Fix:** The generator now produces a private `__DimShim` class for interfaces that have DIM members. The shim:
- Implements the interface with explicit implementations for abstract members only (delegates to stub interceptors)
- Does NOT implement DIM members, allowing the C# runtime to invoke them naturally
- Auto-wires as `_source` on DIM interceptors during construction

Configured interceptors still take priority over DIMs. The `Source(T)` API overwrites the shim, which is the correct behavior.

**Supported DIM member types:** Methods, properties, indexers.

**Affected patterns:** Standalone interface (patterns 1, 2), Inline interface (pattern 5), Open generic interface (pattern 7). Class stubs are unaffected (they already call `base.Method()` correctly).

**Affected pipelines:** `FlatModelBuilder`, `InlineModelBuilder`, `FlatRenderer`, `InlineRenderer`.

**Zero overhead:** The shim is only generated when the interface has DIM members. Existing stubs are unaffected.

## What's Fixed

### Nullable Unconstrained Generic Params in Class Stubs (CS0453)

When a base class declares a generic method with nullable unconstrained type parameters like `virtual TData? NullableValues<TData>(TData? data)`, the generator emitted `TData?` in override methods and delegate signatures. Without a `struct` constraint, the C# compiler interprets `TData?` as `Nullable<TData>`, which is invalid for unconstrained type parameters (CS0453).

**Fix:** The generator now detects unconstrained nullable type parameters in class stub pipelines, strips the `?` annotation, and wraps the affected code with `#nullable disable` / `#nullable restore`. This matches the existing fix for interface stubs (shipped in v0.45.0).

**Affected patterns:** Inline Class (pattern 6), Standalone Class (pattern 3). Both abstract and virtual base classes.

**Affected pipelines:** `ClassModelBuilder`, `StandaloneClassModelBuilder`, `ClassRenderer`.

**Root cause:** The nullable handling logic (`HasUnconstrainedNullableTypeParams` / `StripUnconstrainedNullableAnnotations`) existed in `FlatModelBuilder` and `InlineModelBuilder` for interface stubs but was never added to the class stub builders.
