## Overview

Replace delegate-specific interceptor rendering in `InlineRenderer` (lines 1254--1971, ~718 lines across 8 methods) with a call to the shared `MethodInterceptorRenderer`. **No modifications to MethodInterceptorRenderer are needed** -- the existing `UnifiedMethodInterceptorModel` and `InterceptorRenderOptions` already accommodate the delegate case.

This gives delegates: async auto-wrapping, sequence support, fluent builder chaining, working Strict mode, and eliminates duplicated When chain rendering.

---

## Why This Works Without Modifying MethodInterceptorRenderer

The async auto-wrapping logic is driven by `GetAsyncTypeInfo(model.ReturnType)` which inspects the `ReturnType` string. For `delegate Task<int> AsyncOperation(int x)`, the `ReturnType` is `global::System.Threading.Tasks.Task<int>` -- `GetAsyncTypeInfo` detects `Task<T>`, extracts `int`, and generates the simplified callbacks. No special delegate handling required.

A delegate maps to `UnifiedMethodInterceptorModel` as: **a single non-overloaded method with no declaring interface, no user method, no ref/out, standard Func/Action delegates.**

### Step 2: Rewrite RenderDelegateStub

**File:** `src/Generator/Renderer/InlineRenderer.cs`

Replace `RenderDelegateStub` to:
1. Call the adapter to get `UnifiedMethodInterceptorModel` + `InterceptorRenderOptions`
2. Call `MethodInterceptorRenderer.RenderInterceptorClass(w, model, options)` for the interceptor
3. Render only the delegate stub class shell:
   - `Strict` property (update XML doc to remove "Not yet implemented for delegate stubs" -- Strict now works)

**Critical: The stub's `Invoke()` must NOT call `Interceptor.RecordCall()`.** The current stub calls `RecordCall()` before dispatch, but `Interceptor.Invoke()` handles all tracking internally (per-configuration `RecordCall()`, `_unconfiguredCallCount++`, etc.). Adding an explicit `RecordCall()` would double-count calls and break `Verify(Times.Once)`. The old `RecordCall()` method is not generated by `MethodInterceptorRenderer` -- tracking is entirely internal to `Invoke()`.

The stub class rendering is ~60 lines -- much simpler than the current ~240 lines because dispatch logic moves into the interceptor's `Invoke()`.

## Behavioral Changes

### Non-Breaking (existing code still compiles)

- `OnCall()` changes from returning `void` to returning `MethodCallBuilderImpl` -- existing code discards the return value, so `stub.Interceptor.OnCall(callback);` still works
- `Returns()` changes from returning `void` to returning `MethodCallBuilderImpl` -- same reasoning
- `Verify()` implementation changes internally but functionally equivalent
- `Strict` mode now actually works for delegate stubs (previously declared but non-functional)

### New Capabilities (what delegates gain)

- `Returns(42)` auto-wraps async delegates (no more `Task.FromResult`)
- `OnCall((x) => x * 2)` simplified callback for async delegates
- `Returns(first, params rest)` sequence shorthand
- `OnCall(...).ThenCall(...)` fluent sequence chaining
- `OnCall(...).Verifiable()` fluent verifiable marking
- `TotalCallCount` and per-configuration tracking
- Working `Strict` mode -- unconfigured calls throw `StubException`

## Architect Resolution of Developer Concerns

**Date:** 2026-02-05

All four developer concerns are accepted. The developer's analysis was thorough and correct in every case.

### Concern 1 (Critical): `IncludeStrictParameter` / `StrictAccessExpression` -- ACCEPTED

The developer is right on both points:

**(a)** `StrictAccessExpression` is a required positional parameter in the `InterceptorRenderOptions` record with no default. `MethodInterceptorRenderer.RenderInvokeMethod()` unconditionally emits `if ({options.StrictAccessExpression}) throw ...` at two locations (lines 776 and 842). Passing empty string generates `if () throw ...` (syntax error). There is no conditional guard on `IncludeStrictParameter` around these `StrictAccessExpression` usages. The original plan would have generated code that does not compile.

**(b)** `IncludeStrictParameter: false` is dead code -- zero usages across the entire codebase. Every callsite passes `true`. Using an untested code path in a refactoring that claims "zero modifications to MethodInterceptorRenderer" is contradictory.

**Resolution:** Use `IncludeStrictParameter: true` and `StrictAccessExpression: "strict"` as the developer suggested. The delegate stub's `Invoke()` calls `Interceptor.Invoke(Strict, args...)`, passing the stub's `Strict` property as the first argument. This follows the exact same pattern as all other inline stubs.

**Bonus:** This gives delegate stubs working `Strict` mode for free. The current generated code has `Strict { get; set; }` with an XML doc comment saying "Not yet implemented for delegate stubs." After this change, `Strict = true` correctly causes unconfigured delegate calls to throw `StubException`. The XML doc comment should be updated to match the standard wording.

The InterceptorRenderOptions table in the Model Mapping section has been updated.

### Concern 2 (Minor): `BaseIndent` -- ACCEPTED

The developer verified every inline interceptor callsite: `InlineRenderer.cs` lines 111, 119, 133, 157, and 161 all use `BaseIndent: 2`. The current delegate rendering uses `\t\t` (2 tabs) for the interceptor class declaration, consistent with indent level 2.

**Resolution:** Changed to `BaseIndent: 2` in the InterceptorRenderOptions table. My original reasoning ("nested inside Stubs class inside host class" = 3) was wrong -- the `w.SetIndent(2)` pattern used by all other inline stubs handles this correctly at indent level 2.

### Concern 3 (Minor): `RecordCall` double-counting -- ACCEPTED

The developer correctly identified that:
- The current stub calls `Interceptor.RecordCall(args)` before dispatching via `Interceptor._onCall`
- The new `Interceptor.Invoke()` handles all tracking internally: `_unconfiguredCallCount++`, per-config `_onCallTracking.RecordCall()`, etc.
- Both together = double-counted calls, breaking `Verify(Times.Once)`

**Resolution:** Step 2 now explicitly states that the stub's `Invoke()` must NOT call `RecordCall()`. The stub's `Invoke()` body is simply:
```csharp
private {ReturnType} Invoke({params})
{
    {return} Interceptor.Invoke(Strict, {args});
}
```
No `RecordCall()`, no When chain checking, no dispatch logic. All of that is inside `Interceptor.Invoke()`.

### Concern 4 (Minor): `Returns()` mutual exclusivity semantics -- ACCEPTED as verification gate

The developer's analysis is correct: the current `Returns(value)` is `_onCall = (...) => value` (sets the callback), while the new interceptor's `Returns(value)` sets `_hasReturnsValue = true` and clears `_onCall`. The dispatch priority in the new `Invoke()` is: When chain > sequence > `_hasReturnsValue` > `_onCall` > simplified callback > unconfigured fallback.

The mutual exclusivity tests at `DelegateValueOverloadTests.cs:189-217` test:
1. `Returns` then `OnCall` -- OnCall should win
2. `OnCall` then `Returns` -- Returns should win

In the new interceptor:
- `OnCall(cb)` clears `_hasReturnsValue` and sets `_onCall` (see `MethodInterceptorRenderer.cs` line ~175-183)
- `Returns(val)` sets `_hasReturnsValue = true` and clears `_onCall` (see line ~222-226)

Since each clears the other, the "last wins" semantic is preserved. The dispatch priority does not matter because only one of `_hasReturnsValue`/`_onCall` is active at any time. This should pass. However, per the developer's suggestion, this is now listed as an explicit verification gate in Step 4 -- if the tests fail, STOP and report.
